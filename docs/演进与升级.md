# 演进与升级

个人学习项目，升级标准不是「更能打广告」，而是：**契约更清晰、主链路更稳、面试时能指到代码。**

## 已经做过、值得保留的方向

- 统一 Markdown 投影，避免 CLI 导出和 MCP 阅读不是同一篇文章。
- MCP 副作用拆分：ingest 写、read 只读、summarize 只打模型。
- 长文用 cursor + 章节跳读，而不是服务端偷偷截断或 MapReduce。
- 失败用 isError + `code`，不用 JSON 里的假成功。
- 存储跟协议一起删（FTS），避免死索引。

## 值得做、仍然很小的优化

按投入产出，优先这些，而不是新子系统：

1. **真实文章验收**：链接密、表格/代码块、超长文各一篇，看投影和分页，而不是再加功能。
2. **抓取失败可诊断**：超时、反爬、不是公众号，错误码已经有，日志里不要带正文。
3. **阅读契约打磨**：节名模糊匹配是否过宽、H2 目录是否漏掉只有 H3 的文章（现在会合成「正文」整篇）、文头是否和正文标题重复。
4. **测试**：改投影就补 HTML fixture；不要用跳过测试换绿。

## 可以想、但不要当当前范围

| 想法 | 为什么先不做 |
| --- | --- |
| 多模型摘要 / 本地小模型 | 岗位相关，但会把「一次 JSON 摘要」讲糊；先保 DeepSeek 一条路径 |
| MapReduce 长文摘要 | 成本、失败组合、聚合失真；和「交付原文页」抢定位 |
| 知识库 + 跨文章检索 | 另一类产品；本项目没有权限模型和语料治理 |
| 内部 coding agent | 直接偏离；简历也讲不清和主力项目的关系 |
| Postgres / 多用户 | 没有并发产品需求；SQLite 与端口已经够讲「以后怎么换」 |
| 下载微信图片、OCR | 存储、版权、安全面立刻变大 |
| 公开 block API、文章内搜索 | 协议兼容负担；当前是单篇阅读 |

若以后真要加来源（非微信）或多用户：先写 URL 策略、SSRF、存储隔离，再写功能。不要先加 Agent 平台当「基础设施」。

## 和面试讲解的关系

被问「你接下来怎么升级」时，优先说上面「很小的优化」和「明确不做」。不要许诺知识库或自研 runtime。细节仍以当前代码为准，见 [架构设计](架构设计.md) 与 [MCP构建设计与面试讲述](MCP构建设计与面试讲述.md)。
