# 设计动机与经历

这份文档用第一人称写，方便面试时对着讲。项目是个人学习用的，不是公司生产系统，也不是简历第一项目。

## 我为什么做它

准备 Python Agent 开发面试时，我需要一个**自己能跑通、能改、能讲清楚边界**的小系统，而不是再写一个 ChatBot Demo。

真实痛点很具体：我想让 Cursor 这类 Agent 读微信公众号长文。页面不稳定、HTML 脏、一篇三万字直接塞进上下文也不合适。如果让模型自己打开浏览器抓，我会说不清「这次调用有没有联网、有没有写盘」。

所以目标收成一句话：**做内容交付，不做第二个 Agent。** 把文章变成可缓存的 Markdown 页，让外面的 Agent 按自己的任务去读、去摘要、去记笔记。

## 中间走过的弯路

仓库里一度更接近「Reading Agent 平台」：内部 Agent、Run/SSE/Trace、知识库、评测、多模型、FTS 搜索、MapReduce 长文摘要、证据 block。对学习来说东西很多，对面试叙事来说很危险——听起来像平台，代码却撑不起那个故事，维护也散。

后来主动收缩：

- 删内部 Agent 与评测，避免项目定位变成「我做了个 Agent」。
- MCP 只留四个工具，抓取、阅读、摘要的副作用拆开。
- 摘要只留 DeepSeek 一次调用；超长就失败，不假装全文都总结完了。
- 搜索、公开 block ID、FTS 写入跟着删，避免协议和存储不一致。

收缩本身就是经历：Agent 岗位容易把「能调模型」做成产品全部，我用这个项目练习**少暴露工具、把副作用写进契约**。

## 和岗位的对应关系

面试官若问「你做过 Agent 吗」，比较诚实的说法是：

- 主力经历不在这个仓库。
- 这个仓库证明我理解 **Agent 的外部工具该长什么样**：幂等读、显式写、失败码、不可信网页、上下文预算。
- 我没有在这里实现 agent loop、planning、多 Agent 编排；那些若要讲，应拿别的项目或纸上设计，不要把本仓库说成 runtime。

## 一次具体的产品判断

用本机 MCP 读过约三万字的公众号长文之后，发现顺序 `next_cursor` 能走通，但体验并不好：页从列表中间切开、没有「读到哪」、ingest 把全部 H3 目录一次性给模型、工具说明还在鼓励从头翻到尾。

改动没有加新工具，而是改阅读契约：默认 H2 目录、按节名跳读、软分页、页上带进度、MCP 默认藏图。这和项目定位一致——优化 **Agent 怎么读一篇文章**，而不是让服务替 Agent 读完。
