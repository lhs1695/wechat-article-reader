# 架构设计

## 一句话

把「一篇微信公众号文章」变成可缓存、可分页、可摘要、可导出的内容，三个入口（CLI、`python -m wechat_article_reader web` / `run_web.pyw` / `run_web.cmd`、MCP）走同一套领域服务，而不是三套爬虫。

## 分层

依赖只允许向内：`presentation / mcp → features → application → domain`；`infrastructure` 实现端口，由装配层注入。

```text
presentation/cli    presentation/web    mcp/
        \                 |               /
         \                |              /
          features/article_workflow  +  features/article_reading
                          |
                    application/use_cases + ports
                          |
                         domain
                          ^
                          |
            infrastructure（抓取、DeepSeek、SQLite、导出、配置）
```

| 层 | 职责 | 不该出现 |
| --- | --- | --- |
| `domain` | 文章、URL、正文、摘要值对象 | HTTP、SQL、Click、FastMCP |
| `application` | 抓取 / 摘要 / 导出 / 批处理用例；出站端口 | 具体 httpx、SQLAlchemy 模型 |
| `features` | 给入口用的稳定门面：工作流 + 阅读投影 | 每个 CLI 命令各写一套 HTML 解析 |
| `infrastructure` | 微信抓取、DeepSeek、SQLite、导出、Settings | 业务规则抄一份和 domain 不一致的 |
| `presentation` / `mcp` | 适配人机协议和 Agent 协议 | 直接打公众号 HTML |

三个入口共用同一套文章模型和阅读投影；换 CLI / Web / MCP 不必再解析一遍 HTML。

## 运行时数据流

```text
URL
  → WechatHttpxScraper（域名、SSRF、体积、MIME、HTML 清洗）
  → FetchArticleUseCase
  → SQLite articles
  → ArticleReadingProjector（HTML → 内部 blocks，不落库）
  → MarkdownReadingRenderer
       ├─ MCP / CLI read（分页、按节、文头）
       ├─ Markdown 导出
       └─ SummarySourceRenderer → DeepSeek（可选）→ summaries 表
```

blocks 和章节目录由原文投影产生，不持久化分页结果；服务按 UUID、revision、精确源摘要和 URL 缓存投影，最多 16 篇 / 约 8 MiB，刷新自动失效。SQLite 保存精确原文摘要与不透明 revision；分页绑定 revision，避免刷新后旧 cursor 漏读。URL 查询参数稳定排序统一身份。

摘要保存实际输入摘要和生成条件，以条件匹配复用结果。摘要提交使用 revision 条件更新，仅写摘要；生成期间正文变化会拒绝提交。文章正文缩进、空行或 HTML 变化都会使旧摘要失效，首次缓存时间保持不变。MCP 工作线程接收取消信号，事务提交与文件原子替换前再次检查。

## 两个门面为什么分开

- `ArticleWorkflowService`：人机入口常用的「URL 进来，抓 + 可选摘要 + 导出」。MCP 的 `summarize_article` 走其中的 `summarize_cached`，避免再用 URL 隐式抓取。
- `ArticleReadingService`：Agent 阅读契约。`ingest` 是唯一写缓存的阅读入口；`read` 只拿 UUID；`export_markdown` 把已缓存文章写成 Markdown 文件。

人可以在 CLI 用一个 `fetch` 做完；Agent 必须能分清「这次会不会联网」。

## 阅读投影

1. 清洗后的 HTML 按文档顺序拆成 heading / paragraph / list_item / quote / code / table / image。
2. `sections` 由 heading 推导；对外目录默认压到 H2，若文章没有 H2（例如只有 H3）则对齐到最浅标题，**不**把整篇合成一节「正文」。无 heading、或首个 heading 之前的引言，才用「正文」覆盖那一段。内部仍保留全部 heading 供跳章和软分页。
3. `read` 对正文与文头一起计算预算：`max_chars` 是软上限（默认 20000，范围 1000–20000），完整页硬上限 20000。连续列表尽量整组，溢出时把未写完的 H2/H3 留给下一页。`section` 是精确标题或至少两字的唯一前缀，返回该章及子章节；重名用 `section_start_cursor`。续读 cursor 绑定 revision；越界明确报错。数字和大写词均按原文保留。CLI、Web、MCP 与 Markdown 导出默认无图；阅读页返回省略数量和未读取图像的状态。
4. 页响应带 `block_count`、`word_count`（本页投影正文长度）、`section_title`、`section_end_cursor`、`chars`。覆盖节是合成「正文」时，元数据保持「正文」，续页不插入 `# 正文`。首页补标题/作者，若首块 heading 已等于文章标题则只补作者、不重复标题。后续页仅在真实节名时补 heading。这些都不入库。
5. 投影保留账号文末推荐内容和正文结尾，不按启发式删除；识别到明确推荐标记时附 `content_notes`。

投影区分普通文本与完整结构：代码保留原始空白并动态生成围栏，表格保持整块，列表和引用持有子节点。普通段落的连续分块在整篇渲染时重新拼接；分页仍使用顶层块索引。嵌套节点、语言标记、列表编号和连续标记仅供内部渲染，不扩展对外 API。

转换目标为 GFM。简单表格按单元格转义；合并单元格或嵌套表格使用清洗后的 HTML，默认无图仍适用。复杂表格的额外文本序列化暂不实施。代码保留 NBSP，普通文字跨 span 的特殊符号整体转义，CSS 语义样式转为安全标签。格式回归检查渲染后的 DOM、代码精确文本和元数据转义。

公开契约包含 Markdown 页、revision、next_read、标题或位置章节选择、章节范围与图像阅读状态。block id 不对外。脏 DOM 样例在 `tests/fixtures/html/`，回归用例另覆盖并发、取消与持久化版本。

## 持久化

SQLite 当前表：`articles`、`summaries`。用 Alembic 迁移。曾经为搜索加过 FTS，工具删了之后迁移里删掉 FTS，避免「协议没了、索引还在写」。

没有独立操作历史表。历史页展示的是缓存里的文章，以及当前正文 hash 是否已有摘要。

本地单用户：零运维、可事务。存储通过端口抽象；真要多用户再换引擎，而不是先上集群。

## 安全（和架构绑在一起）

抓取不是「能打开网页就行」：

- 只允许微信公众号 host。
- SSRF / DNS 重绑定检查。
- 限制重定向、响应字节、正文字符数、内容类型；公众号抓取的每一跳重定向仍须指向 `mp.weixin.qq.com`。
- HTML 清洗；图片只保留 https URL。
- 普通网页文字按 Markdown 字面文本投影，只有真实 HTML 链接才生成 Markdown 链接。
- 摘要读取按当前正文 hash 匹配；刷新正文不会复用旧摘要。
- MCP 五个工具成功体都带 `source_trust: untrusted_web_content`（摘要是基于不可信正文的二次生成，同样标记）。
- 远程 MCP HTTP 必须配置令牌；远程导出限制在配置的导出目录内。

摘要密钥只在环境变量里。日志和仓库都不能出现 Key、文章全文或 Trace。

## MCP 在架构里的位置

`mcp/` 是适配层，不是第二套业务。它做三件事：参数校验、把领域异常映射成 `code: 说明` 的 isError、声明副作用。传输是 stdio 或本机 Streamable HTTP，不改变阅读服务。

工具名单、副作用和失败码以根目录 [README](../README.md) 的 MCP 表为准。`mcp/` 不解析 HTML，也不单独实现摘要。
