# 架构设计

## 一句话

把「一篇微信公众号文章」变成可缓存、可分页、可摘要、可导出的内容，三个入口（CLI / Web / MCP）走同一套领域服务，而不是三套爬虫。

## 分层

依赖只允许向内：`presentation / mcp → features → application → domain`；`infrastructure` 实现端口，由装配层注入。

```text
presentation/cli    presentation/web    mcp/
        \                 |               /
         \                |              /
          features/article_workflow  +  features/article_reading
                          |
                    application/use_cases + ports
                          |
                         domain
                          ^
                          |
            infrastructure（抓取、DeepSeek、SQLite、导出、配置）
```

| 层 | 职责 | 不该出现 |
| --- | --- | --- |
| `domain` | 文章、URL、正文、摘要值对象 | HTTP、SQL、Click、FastMCP |
| `application` | 抓取 / 摘要 / 导出 / 批处理用例；出站端口 | 具体 httpx、SQLAlchemy 模型 |
| `features` | 给入口用的稳定门面：工作流 + 阅读投影 | 每个 CLI 命令各写一套 HTML 解析 |
| `infrastructure` | 微信抓取、DeepSeek、SQLite、导出、Settings | 业务规则抄一份和 domain 不一致的 |
| `presentation` / `mcp` | 适配人机协议和 Agent 协议 | 直接打公众号 HTML |

三个入口共用同一套文章模型和阅读投影；换 CLI / Web / MCP 不必再解析一遍 HTML。

## 运行时数据流

```text
URL
  → WechatHttpxScraper（域名、SSRF、体积、MIME、HTML 清洗）
  → FetchArticleUseCase
  → SQLite articles
  → ArticleReadingProjector（HTML → 内部 blocks，不落库）
  → MarkdownReadingRenderer
       ├─ MCP / CLI read（分页、按节、文头）
       ├─ Markdown 导出
       └─ SummarySourceRenderer → DeepSeek（可选）→ summaries 表
```

blocks、content hash、章节目录都是**读取时现算**，不单独持久化分页结果。缓存命中比的是 URL（及刷新策略）和正文 hash（摘要是否过期），不是「上次 Agent 读到第几页」。

## 两个门面为什么分开

- `ArticleWorkflowService`：人机入口常用的「URL 进来，抓 + 可选摘要 + 导出」。MCP 的 `summarize_article` 走其中的 `summarize_cached`，避免再用 URL 隐式抓取。
- `ArticleReadingService`：Agent 阅读契约。`ingest` 是唯一写缓存的阅读入口；`read` 只拿 UUID。

人可以在 CLI 用一个 `fetch` 做完；Agent 必须能分清「这次会不会联网」。

## 阅读投影

1. 清洗后的 HTML 按文档顺序拆成 heading / paragraph / list_item / quote / code / table / image。
2. `sections` 由 heading 推导；对外目录默认压到 H2，若文章没有 H2（例如只有 H3）则对齐到最浅标题，**不**把整篇合成一节「正文」。无 heading、或首个 heading 之前的引言，才用「正文」覆盖那一段。内部仍保留全部 heading 供跳章和软分页。
3. `read` 按块累加渲染长度，硬顶仍是 `max_chars`（1000–20000）和单块 20000。软边界：连续 `list_item` 尽量整组；溢出时尽量把未写完的 H2/H3 留给下一页。`section` 是精确标题，或至少两字的唯一前缀；单字前缀不算匹配。
4. 页响应带 `block_count`、`word_count`、`section_title`、`chars`；首页补标题/作者，若首块 heading 已等于文章标题则只补作者、不重复标题。后续页在需要时补当前节名。这些都不入库。

公开承诺只有：Markdown 页 + cursor/next_cursor + 可选 section 名。block id 不对外。脏 DOM 样例在 `tests/fixtures/html/`，用来对表格、代码块、文末推荐链接和超长块，不为验收另开工具。

## 持久化

SQLite 当前表：`articles`、`summaries`。用 Alembic 迁移。曾经为搜索加过 FTS，工具删了之后迁移里删掉 FTS，避免「协议没了、索引还在写」。

没有独立操作历史表。历史页展示的是缓存里的文章，以及当前正文 hash 是否已有摘要。

本地单用户：零运维、可事务。存储通过端口抽象；真要多用户再换引擎，而不是先上集群。

## 安全（和架构绑在一起）

抓取不是「能打开网页就行」：

- 只允许微信公众号 host。
- SSRF / DNS 重绑定检查。
- 限制重定向、响应字节、正文字符数、内容类型。
- HTML 清洗；图片只保留 https URL。
- MCP 把正文标成 `untrusted_web_content`。

摘要密钥只在环境变量里。日志和仓库都不能出现 Key、文章全文或 Trace。

## MCP 在架构里的位置

`mcp/` 是适配层，不是第二套业务。它做三件事：参数校验、把领域异常映射成 `code: 说明` 的 isError、声明副作用。传输是 stdio 或本机 Streamable HTTP，不改变阅读服务。

工具名单、副作用和失败码以根目录 [README](../README.md) 的 MCP 表为准。`mcp/` 不解析 HTML，也不单独实现摘要。
